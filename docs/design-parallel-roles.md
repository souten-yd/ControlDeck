# 並列のスロット数に応じた役割分担（設計と第 1 段）

作成: 2026-11-23。起点は利用者の要望（同日）。

> 「調査やディープリサーチのとき、5 並列で実行できるなら、1 並列でメインの会話を続け、残りの 4 並列で調査の要約などのタスクを分け、並列数を無駄に使わないようにできないか。並列数は事前の設定を読む。並列 1 は従来どおり、2 以上ならメインの会話と調査・要約を並べて実行できるように。OpenCode の開発でも、計画は大きなモデル、実装は Radiance の 5 並列、最後にまた大きなモデルで整合性を評価し、直しは開発用へ戻す流れにできないか。1 つ目が会話、2 つ目が検査、3 つ目が調査、のように並列数に応じて適切に動かしたい。」

## 1. 今の作り（調べた結果）

### 1.1 並列数（スロット）を読める場所

各ランタイムの `list_instances()` が、登録から共通の `n_parallel` を返す。`local_llm.list_instances()` がこれらをまとめる。

| ランタイム | `n_parallel` の元 | 並列で合計が伸びるか（2026-11-15 実測） |
|---|---|---|
| Radiance | 登録の `max_num_seqs`（`radiance.py` の `_present`） | 伸びる（1 本 177 → 6 本で合計 577 tok/s） |
| llama.cpp | 登録の `n_parallel`（`--parallel`。`/slots` で空きも見える） | 伸びる |
| Strata | 登録の `parallel`（1〜8。`strata_gateway.py`） | 伸びない（並列にしても合計が増えない） |
| Maya-S | 常に 1 を返す | 並列では起動しない |

- 画面の状況表示（`models_mgmt/router.py` のエンドポイント一覧）は `slots` / `busy` / `accepting` を持つ。llama.cpp は `/slots` の実測、他は ControlDeck が中継した本数（`live_stats`）。**今動いている空きスロットも取れる**。
- 注意: `swap_scheduler.py` は「同じモデルを並列に実行するのは Radiance だけ」と見なし、llama.cpp も 1 本とする。第 1 段は実測（llama.cpp も伸びる）に合わせて llama.cpp も数える。両者の差は第 2 段で揃えるか決める（5.3）。

### 1.2 どこで LLM を何本同時に呼んでいるか

- 調査（`workflows/research_intent.py`）: 依頼の理解 1 回 → 検索 → 選別（reranker）→ ページ読み取りを固定 4 本（`READ_PARALLEL`） → 足りない観点の判定 1 回（最大 rounds-1 回）。LLM の呼び出し自体は逐次で、同時に走るのは読み取り（HTTP と reranker）。
- 会話の生成（`chat_persist.py`）: 調査の後に同じモデルへ 1 本。調査中と生成中が重なることは今はほぼ無い（逐次）。
- ワークフロー（`engine.py`）: `MAX_PARALLEL_NODES` の Semaphore でノードを並列に流す。モデルのスロット数とは無関係の固定値。
- OpenCode（`integrations/opencode/provider.py`）: 主のエージェント（build / plan）と子エージェント（`mode: subagent`、reviewer・ui-verifier など）があり、役割ごとにモデルを指定できる（`models_mgmt/role_presets.py` は埋め込み・reranker の既定。OpenCode の役割別モデルは provider 側）。子の同時数はモデルのスロット数を見ていない。
- 調べて分かった点: 調査の同時 4 本は HTTP と reranker の読み取りで、チャットの LLM は使っていない。観点ごとの LLM 処理は今は無く、LLM を呼ぶのは理解と判定の逐次の呼び出しだけ。

## 2. 他の仕組み（公開されている仕様の理解。今回は Web の再確認はしていない）

| 仕組み | 要点 | ここへ活かすこと |
|---|---|---|
| Claude Code の subagents | 主の会話が子へ作業を委譲し、子は別の文脈で動いて要約だけ返す。子ごとにモデルを選べる | 会話の LLM が親、調査・要約は子。子の結果は要約で返し、親の文脈を汚さない |
| OpenCode の subagents | 主のエージェントと `mode: subagent` の子。設定でモデル・道具を分ける。ControlDeck は既に使っている | 第 2 段で役割ごとのモデルを「並列数」から割り当てる |
| Aider の architect / editor | 推論に強い大きなモデルが方針を書き、安いモデルが編集を実行する 2 段 | 計画（大）→ 実装（Radiance の並列）の根拠 |
| vLLM の並列 | 連続バッチ（continuous batching）。`max-num-seqs` 本までは 1 本あたりの速度が落ちにくく合計が伸びる | Radiance の並列が伸びる理由。スロット数＝`max-num-seqs`。上限を超えると待ち行列になる |

これらの共通点は「会話の主が計画・判断を持ち、量の多い下働きは別のスロット（または別のモデル）へ回し、結果を要約で受け取る」こと。

## 3. 案の比較

### 案 A: 会話の LLM がルーター（子のタスクを空きスロットへ動的に割り当て）
- 良い点: 状況に応じて柔軟。空いていれば全部使える。
- 悪い点: ルーター自身が 1 スロットを占め、判断の LLM 呼び出しが増える。誤った分担で品質が揺れる。実装・試験が大きい。
- 判定: 柔軟だが重い。第 1 段には不向き。

### 案 B: 決まった役割の割り当て（会話 1・裏の作業 n-1）
- 良い点: 規則だけで決まる（LLM 不要）。説明しやすく、試験しやすい。並列 1 は従来どおりにできる。
- 悪い点: 裏の作業が無いとき残りが遊ぶ（無駄に使わない目的には、別の用途へ貸す余地を残す）。
- 判定: 第 1 段に採用。調査から始める。

### 案 C: OpenCode の「計画 → 並列で実装 → 整合性の確認 → 直しは実装へ」
- 流れ: 大きいモデルが計画と分割 → 実装用モデル（Radiance の n 並列）が分割ごとに実装 → 大きいモデルが整合性を確認 → 指摘は実装へ戻す。
- 最大の問題はモデルの載せ替えの費用。1 枚の GPU で大きいモデルと Radiance は同時に載らないことが多く、載せ替えは数十秒〜分かかる。計画・確認の各段で載せ替えると、並列で得た時間を食う。
- 判定: 効果は大きいが段階が必要。第 2 段以降で、載せ替えの回数を最小にする（計画 1 回 → 実装 → 確認 1 回）形で。

### 並列で伸びないランタイム（Strata・Maya-S）
- 並列にしても合計が増えず、むしろ 1 本あたりが遅くなる。役割分担の対象にしない（裏の作業も 1 本。並列 1 と同じ扱い）。
- 別のモデルを同時に載せる余地（小さい要約用モデルを別に常駐）は GPU の空き次第。常駐の追加は費用が高く、第 3 段で測ってから。

### 並列 1 のとき
今のまま。調査は 1 本ずつ、会話と取り合わない。

## 4. 推奨

案 B（規則で決める）を土台に、案 C を段階で足す。案 A のルーターは、案 B の割り当てで足りない場面（実測で偏りが出たとき）が見えてから。

- 役割の数え方（スロット数 n）:
  - n = 1: 会話と裏の作業は交互（従来どおり）。
  - n >= 2: 会話 1 + 裏の作業 n-1（上限 8）。
  - 伸びないランタイム: n を 1 として扱う。
- 並列を使い切らない。利用者が「無駄に使わない」と言うため、裏の作業が無い間のスロットは何もしない（先読みで埋めない）。

## 5. 段階の計画

### 第 1 段（実装済み）: 調査で LLM を呼ぶ処理の同時数をスロット数から決める
- 方針（2026-11-23 レビューで修正）: ページの読み取り（`read_and_judge`。HTTP と reranker だけでチャットの LLM を使わない）はスロットと無関係なので、これまでどおり `READ_PARALLEL`（4 本）。スロットで絞るのは LLM を呼ぶ処理だけ。
- `backend/app/models_mgmt/parallel_slots.py`（新規）: `slots_of`（ランタイムで 1 か n）・`helper_slots`（n-1、上限 8）・`background_parallel(base_url, model, override)`。モデルは宛先のポート（`local_llm.instance_for_port`）か別名（`local_llm.find`）で特定する。特定できない・設定が壊れているローカルは 1 本。外部 API はスロットを持たないので従来の 4 本。
- `workflows/research_intent.py`: `investigate` の観点ごとの処理（選別 → ページ読み取り → その観点の LLM 処理 `digest`）を、観点をまたいで並べて走らせる。ページ読み取りは観点をまたいで共有の Semaphore で総数 `READ_PARALLEL`、`digest`（LLM を呼ぶ処理）は `background_parallel` 本までの Semaphore。並列 1 なら LLM 処理は順に。観点をまたぐ重複 URL の除外は並べる前に順に決める。足りない観点の判定 `_evaluate` は 1 回の呼び出しなのでそのまま。
- 現状 `digest` は未接続（None）。今の調査にはチャットの LLM で観点ごとに要約する処理がまだ無く、第 2 段で接続する。第 1 段は、その受け皿（本数の決め方・Semaphore）と設定・試験までを入れた。
- 設定: 設定 → API キー → 調べる量 に「LLM を同時に使う本数」（`research_keys.LIMITS["llm_parallel"]`、0〜8、0 は自動）。0 以外は上書きで、スロット数と 8 を超えない。伸びないランタイムは上書きでも 1。
- 会話の生成と裏の LLM 処理がスロットを取り合わない: 本数が n-1 までなので、会話の 1 本分は常に空く。
- 見えるようにする点（同時数の画面表示）は第 1 段では入れていない。

### 第 2 段: 調査の要約・判定の LLM 呼び出しを裏のスロットへ
- `digest` に観点ごとの要約・判定を接続する（観点は最大 4 で、n-1 本まで並列）。
- 変えるファイル: `workflows/research_intent.py`（`_evaluate` を観点ごとの並列に分ける）、`workflows/chat_persist.py`（最終の答えの生成は会話の 1 本だけ）。
- 会話が走っている最中は裏を止める判断が要るため、`models_mgmt/router.py` の `busy` / `accepting` を見て空きがあるときだけ投入する（`parallel_slots` に `free_slots(base_url, model)` を足す）。
- 測ること: 調査の合計時間、会話の最初のトークンまでの時間（TTFT）、会話の tok/s（裏が走っていないときとの差）、スロットの `busy` の推移。

### 第 3 段: OpenCode の役割の流れ（案 C）
- 利用者が選ぶ設定の形（設定 → 開発（OpenCode））:
  - 「計画・確認のモデル」（大きいモデル）、「実装のモデル」（Radiance など）、「実装の並列数」（自動＝スロット数 -1、または固定）。
  - 「載せ替えの方針」: 一度に 1 往復（計画 → 実装 → 確認）／確認を省く／載せ替えない（実装モデルが計画も担当）。
- 変えるファイル: `integrations/opencode/provider.py`（`payload["agent"]` へ plan・build・実装の子・reviewer のモデルを並列数に応じて入れる。`_delegated_agents` を拡張）、`models_mgmt/swap_scheduler.py`（役割ごとの要求を載せ替えの回数を最小にして順番づけ。`parallel` の定義を Radiance だけでなく llama.cpp にも揃えるか決める）、`models_mgmt/role_presets.py` またはその隣に役割の既定を追加、フロントの設定画面。
- 流れ: 計画（大・1 回）→ 分割された実装タスクを n 本並列で（Radiance）→ 大きいモデルへ載せ替えて整合性の確認 1 回 → 指摘があれば実装へ戻す（載せ替えは往復ごとに発生するため、直しが小さいときは大きいモデルで直す選択を残す）。
- 測ること: 載せ替えにかかった秒数、各段の所要時間、実装の合計 tok/s（1 本のとき・n 本のとき）、手戻りの回数、最終のテスト合格までの時間。載せ替えの回数 × 秒と、並列で得た時間の差し引きで、利用者に「この流れが得か」を見せる。

### 第 4 段（必要なら）: 案 A（会話の LLM がルーター）
- 第 2〜3 段の実測で、決まった割り当てでは偏る場面が出たときだけ。会話の LLM が「検査・調査・実装」のどれに回すかを構造化出力で決める。ルーター自身の呼び出しの費用（トークン・時間）を測り、規則より得なときだけ使う。

## 6. 試験（第 1 段）
`backend/tests/test_parallel_slots.py`
- ランタイムごとの本数（Radiance 5 → 4、llama.cpp 3 → 2、並列 1 → 1、Strata・Maya-S → 1、上限 8、不正な値 → 1）。
- 設定の上書き（スロット数・8 を超えない、0 は自動、伸びないランタイムは 1）。
- 設定が読めないとき: ローカルは 1、外部 API は従来の 4。モデルの別名での特定。
- 設定値 `read_parallel` の範囲（0〜8）。
- ページ読み取りはスロット 1 でも 4 本同時で、観点が並んでも総数 4 本。LLM を呼ぶ処理の同時数が n-1 を超えず、並列 1 で順に走ること（モックで最大同時数を計測）。

## 7. 未解決・判断
- 解決済み（2026-11-23）: 読み取りと LLM の本数を分けた。ページ読み取りは 4 本固定、スロットで決めるのは LLM を呼ぶ処理だけ。並列 1 でも調査は遅くならない。
- 並列で伸びない Strata に、小さい要約用モデルを別に常駐させる案の費用対効果（VRAM と常駐の電力）。
- `swap_scheduler` と `parallel_slots` で「並列で伸びるランタイム」の定義を 1 か所にまとめる（5.3 に相当。第 3 段）。
