# 開発・PR・マイルストーン・リリース運用（ControlDeck）

2026-11-12 に制定。開発エージェント、Codex、レビュアーは常に本手順を適用する。

## 基本規則

1. 作業開始前に `main` の現行実装、`AGENTS.md`、関連仕様、既存テストを読む。変更範囲と Do NOT、期待される最終状態をPR本文で定義する。
2. 変更は機能単位のブランチとPRに分離する。PR本文の説明だけでは完成と判定しない。実コード・manifest・UI・docs・tests・runtime の相互整合を確認する。
3. 開発完了の判定条件は、対象テストと全体回帰テスト、Frontend build、関係する実機/UI（モバイル幅を含む）を検証し結果を記録すること。未実施項目がある場合、検証済みと表現しない。
4. レビューで scope / allowed / Do NOT / expected final state と差分を照合する。安全性、認証、既定動作、過剰実装、旧文言、非互換性、移行/ロールバックを確認する。
5. 検証に合格したPRだけを **main にマージ**する。CI不在、テスト失敗、実機未確認などが残る場合は、draft PRのまま保持して完了扱いしない。
6. **定義したマイルストーンに到達したら、main のマージ済みコミットを根拠としてGitHub Releaseを発行する。** PRを単にマージしただけでリリース済みとみなさない。マイルストーン未達なら無理にリリースしない。
7. リリースは番号付きタグ `ControlDeck_vX.Y[.Z]` を用い、現在の配布方法（ソースアーカイブ）を維持する。タグのSHA、対応PR、変更点、更新/復旧方法、テスト結果、既知の未検証項目をRelease Notesと `docs/implementation-status.md` に記す。
8. マージ・タグ・GitHub Release発行後に、最新 `main` とReleaseのタグSHA、リリースの存在、内容を直接再確認して報告する。GitHub Releasesに存在しない状態で「リリース済み」と報告しない。
9. 予期せぬ不具合は安易な直接pushで解消せず修正PRにする。小修正なら次のPRにまとめ、要件や安全条件が競合するものだけ別PRを認める。

## CIのコスト管理とLocal First（必須）

- **検証の第一候補は開発者が所有するPC・自前のUbuntu環境**とする。PR作成・レビュー依頼・有料CI実行より前に、関係する単体／統合テスト、Python構文検査、TypeScript本番ビルド、変更機能の実機テストを、可能な範囲でローカル実行する。
- 最初は変更箇所の集中テストを実行し、問題を修正後に全体回帰テストを行う。失敗のたびにGitHub Actionsを起動してはいけない。ローカルで再現・修正できる失敗は、ローカルで解決する。
- **GitHub Actionsの push／pull_request／schedule 自動実行を既定で禁止**する。原則 `workflow_dispatch` の手動実行のみとし、ジョブ単位で必要な最小限の範囲を選択する。外部の既存CIがある場合も無断で有効化しない。
- 有料CIを使うのは、ローカル検証が完了しGitHub環境での最終確認が必要な場合、または自前環境で検証不能なプラットフォーム等の場合だけとする。文書のみのPRは原則CIを起動しない。
- PR更新のたびの自動再実行、失敗ジョブの無制限再試行、毎コミット全テスト実行を禁止する。必要な確認をまとめ、可能ならマイルストーン前に1回の手動実行で確認する。実行前に必要なjobと課金の有無を確認する。
- ローカルで実行したコマンド、テスト件数・結果、ビルド、実機のCPU/GPU/OS、未検証項目をPRまたは `docs/implementation-status.md` に記録する。**GitHub Actionsの成功は自前のR9700実機テストの代わりにならない**。実施していないテストを「確認済み」と書かない。
- 開発エージェントが利用者の自前PCにアクセスできない場合は、その制約を明記し、再現可能なコマンドと期待結果を提示する。自前環境の検証を省略したまま、CIだけを根拠にmainへマージしない。
- GitHub Actionsを一度も利用しないことが目的ではなく、**費用を抑えつつ品質を確保**することが目的である。必要な最終CIは手動で、対象と実行理由を記録して使う。

## ControlDeck 本体アップデートの安全条件

- 更新は明示操作のみ。起動時、自動同期、設定画面表示だけで `git pull` や `npm build` を実行しない。
- 信頼する配布元は `souten-yd/ControlDeck` の正式公開Releaseのみ。任意のURL・任意のshell・任意branchをアプリの更新APIから受け取らない。
- リリース有無確認、現在のバージョン・差分表示、更新実施、結果確認を別操作とする。
- 未コミット変更、追跡先不一致、既存処理の実行中、ディスク不足など危険条件では適用を止め理由を表示。
- 明示的なバックアップ、既存設定・DB・モデル・Add-on保持、失敗時のrollback可能性、再起動後の実ヘルスチェックが必要。
- 本体更新処理の実装が未検証の段階では、更新を実行するUI/APIを有効化せず、手動の `./deck.sh` 更新手順を案内する。
- Strataなどの外部推論ランタイムの導入・更新・削除は本体更新と独立。外部ランタイムの更新でControlDeck本体を変更しない。

## マイルストーンに向けたチェックリスト

- [ ] 計画したスコープを満たすPRがすべてマージされ、未完了の必須項目がない
- [ ] mainのテスト・buildが成功し、実機・モバイルの検証状況を記録
- [ ] 移行・セキュリティ・既定動作・データ保護を確認
- [ ] リリースタグは main の検証済みコミットを参照
- [ ] Release Notes、対応PR、既知の制限、復旧手順を記載
- [ ] GitHub Releaseの公開・タグ一致を再確認
