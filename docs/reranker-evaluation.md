# reranker の評価（2026-11-20）

利用者「reranker はそもそも要るのか。要るならどれぐらいの容量が要るか。軽量化を検討したい。精度は高く、なるべく軽量・高速、
できれば GPU に置かず CPU で動かしたい。別の reranker も想定したい。Web で同じ現象が無いか、あるべき姿も確認して」。

## 今の reranker が遅かった理由（同じ現象の確認）

本番は Qwen3-Reranker-4B（Q4_K_M、llama.cpp）を `--flash-attn off` で起動していた。15 文書の並べ替えが 18.5 秒、
on にすると 1.2 秒（点数は同じ）。全層を GPU に載せても off なら 18〜23 秒で、塊の大きさ（ubatch）は関係なかった。
off は llama.cpp 統合時の既定値が意図なく残っていたもの（PR #477 で reranker だけ on にした）。

Web では「flash-attn off で reranker が遅い」という直接の報告は無かったが、公開されている構成例はどれも
`--flash-attn on` で、古い設定に off が残って遅くなる例は報告されている。CPU での比較記事では、bge-reranker-v2-m3 は
Qwen3-Reranker-0.6B と精度がほぼ同じで約 3 倍速いとされていた。

## 分かったこと

- 日本語の並べ替えは ruri が最良（今の 4B より +0.13）。CPU だけで 32 件 1.1 秒、VRAM を使わない。
- 英語は Qwen 系と bge が強い（0.60〜0.63）。ruri と日本語専用の系列は 0.55〜0.57。
- 「さっき調べた番組表」のように会話の流れを指す質問は、Qwen 系だけが高い点を付けた。ruri は番組表の資料を 1 位に
  並べるが点数は 0.02 で、挨拶（0.014）と見分けられない。直前の話題を質問に添えると 0.47 に上がるが、挨拶も 0.19 に上がる。
  → ruri は「並べ替え」には最良、「点数で入れる・入れないを決める門」には向かない。
- ruri の int8 は動く（下の「int8 化」）。最初に「動かない」としたのは評価の書き方の誤りだった。

## 要るのか・容量

- 会話の資料は 45 会話中 38 が小さく、PR #477 で探さずに全部入れるので、会話では大きい資料の 7 会話でだけ使う。
  Knowledge（RAG）と Workflow の RAG ノードでは引き続き使う。
- 今（Qwen3-Reranker-4B Q4_K_M、ctx 8192）: VRAM 約 3〜4 GB（重み 2.4 GB＋KV）。使うたびに起動し、止まっていれば起動待ちが加わる。
- ruri に替えると: VRAM 0、RAM 約 2.6 GB（fp32）、CPU 8 スレッドで 32 件 約 1 秒。

## int8 化と、実際の長さでの速さ（2026-11-20 追記）

利用者「ruri の int8 化はなぜ動かないのか、調べて解決策を」。

**動かなかった理由**: ModernBERT の問題ではなく、評価の書き方の誤り。sentence-transformers の CrossEncoder の
`model` を量子化したモデルで差し替えたため、入力の辞書がそのまま `input_ids` に渡り `AttributeError` で落ちていた。
中のモデルだけを量子化すれば動く。

**精度**（上と同じ JQaRA 60 問・AskUbuntu 100 問。資料は 1024 トークンまで）:

| 方式 | 日本語 JQaRA | 英語 | ファイル | メモリ |
|---|---|---|---|---|
| PyTorch fp32 | 0.877 | 0.582 | 1.26 GB | RAM 2.5 GB |
| ONNX fp32 | 0.877 | 0.582 | 1.26 GB | RAM 2.8 GB |
| PyTorch 動的 int8 | 0.804 | 0.503 | — | RAM 3.3 GB |
| ONNX 動的 int8（全部） | 0.834 | 0.550 | 0.32 GB | RAM 1.9 GB |
| ONNX 動的 int8（MLP だけ / QKV 以外 / 端の層以外） | 0.836〜0.843 | 0.54〜0.55 | — | — |
| **ONNX 動的 int8（MLP の出力側 Wo だけ fp32）** | **0.875** | **0.581** | 0.73 GB | RAM 2.1 GB |
| ONNX 重みだけ 8 bit（MatMulNBits） | 0.877 | 0.579〜0.581 | 0.58 GB | RAM 1.9 GB（速くならない） |

全部を int8 にすると 0.04 落ちる。原因は MLP の出力側（Wo）: 入力が GeGLU の出力で外れ値が大きく、
活性を 1 つの尺度で 8 bit にすると潰れる。Wo だけ fp32 に残すと fp32 と同じ精度（0.875）で、fp32 より 1.3〜1.4 倍速い。
→ **採用: Wo だけ fp32 の ONNX int8**。実行環境は onnxruntime・tokenizers・numpy だけ（torch は要らない）。

**実際の長さでの速さ**（会話の資料の断片に近い約 800 文字＝質問込み 433 トークン、8 スレッド）:

| | 8 件 | 16 件 | 32 件 |
|---|---|---|---|
| ruri int8（Wo fp32）、資料 1024 トークンまで | — | 4.4 秒 | 8.2 秒 |
| 〃、384 トークンまで | 1.2 秒 | 2.9 秒 | 5.7 秒 |
| 〃、256 トークンまで | 0.7 秒 | 1.65 秒 | 3.3 秒 |
| ruri fp32（ONNX）、1024 まで | — | 5.6 秒 | 10.3 秒 |
| Qwen3-Reranker-4B（GPU、flash-attn on） | — | 1.9 秒 | 3.8 秒 |

上の表の「32 件 1.09 秒」は短い資料での値で、実際の断片の長さでは CPU の ruri は GPU の 4B の約 2 倍かかる。
16 スレッドは 8 スレッドより遅かった（物理 8 コア）。8 件ずつの方が 16 件ずつより速い。

GPU の 4B も、会話の資料（候補 32 件）では 3.8 秒で 3 秒の上限を超えていた（並べ替えずに検索の順で入っていた）。
→ 会話の資料では候補を top_k×2 件（16 件）・各 256 トークンに絞って 1.65 秒で収める。Knowledge・Workflow（上限なし）は
候補 32 件・384 トークン（約 5.7 秒）。

## 会話で毎回探すか（2026-11-20 追記）

利用者「調査のときは使うかもしれないが、それ以外は前の会話の文脈で答えるはず。毎回チェックする必要はない。Claude と同じ方法で」。

- Claude: 資料が文脈に収まるなら全部を文脈に入れ、検索しない。収まらないときだけ検索の道具を持たせ、モデルが要ると判断したときに
  呼ぶ（毎回すべての資料は調べない）。前に調べた結果は会話の中に残り、続きの質問はそれで答える。

  ローカル LLM の会話にはモデルが道具を呼ぶ仕組みがまだ無いので、言い方で判断している。

GPU も許可するが容量は小さい方がよい（ruri でも 1 GB なら GPU でよい）」。

**分かったこと**
- 日本語は ruri が全条件で最良。英語は Qwen3-4B が最良だが、ruri も標準の長さで 0.94（4B 0.97）と近い。
- ruri は GPU なら 32 件 0.2〜0.4 秒（CPU の 20〜40 倍、今の 4B の約 10 倍速い）で、VRAM は 1.4〜1.5 GB（今の 4B の半分以下）。
- llama.cpp で ruri を動かすと点数がずれる: llama.cpp は ModernBERT の reranker を全トークンの平均で読むが、ruri は先頭（CLS）で
  読むよう学習されている（`classifier_pooling: cls`）。変換（SentencePiece の語彙）は通るが、llama.cpp 本体の修正が要る。
- ONNX Runtime MIGraphX: 形（件数 × 長さ）ごとにコンパイルが要る（初回 38 秒）。形を 8 × 1024 の 1 つに固定し、コンパイル結果を
  保存すれば次からは 1.5 秒で使える。形を 2 つにしてキャッシュを使うと結果が壊れた（取り違え）ので、形は 1 つに固定する。
  読み込み時の RAM が最大 6.3 GB（fp32 の ONNX を読むため）。
- 今の会話の資料の区切り（800 文字・重なり 100）は日本語で約 430 トークンで、一般的な 512 前後に収まる。reranker には 1024 トークンまで
  読ませ、標準の塊を切らない。候補は top_k×4（16〜32 件、一般的には 20〜50 件）。

**調べたこと（Web）**: 区切りは 512 トークン・重なり 10〜20% が一般的な出発点（Azure 512/25%、Bedrock 約 300/20%、Vertex 1024/256）。
Anthropic の Contextual Retrieval の例は 800 トークンの塊。並べ替えの効果は候補の上位 30〜50 件でほぼ出る。Claude の Projects は、資料が
文脈に収まる間は全部を文脈に入れ、収まらなくなると検索の道具（project knowledge search）に切り替えて、要るときに検索する。

## ruri を GPU で動かす・GPU での量子化（2026-11-20 追記）

利用者「ruri を GPU で動かす選択肢を。GPU で int8 などに量子化して容量を下げられないか。精度と速さは維持して」。
ONNX Runtime の MIGraphX 版（AMD GPU、計算は fp16）、R9700、資料は 1024 トークンまで、形は件数 × 1024 に固定。

| ファイル | ファイルの大きさ | 日本語・短い / 標準 | 英語・短い / 標準 | 標準の長さ 32 件 | VRAM |
|---|---|---|---|---|---|
| fp32（元の精度） | 1.26 GB | 0.877 / 0.964 | 0.582 / 0.935 | 0.37 秒 | 1.52 GB |
| **fp16** | **0.63 GB** | **0.877 / 0.964** | **0.582 / 0.935** | **0.37 秒** | 1.52 GB（4 件ずつなら **1.27 GB**） |
| int8（CPU 用と同じ） | 0.73 GB | — | — | 3.15 秒 | 1.35 GB |

- **fp16 を採用**: 精度・速さは fp32 と同じで、ファイルは半分。4 件ずつ並べると VRAM 1.27 GB で速さは同じ（2 件ずつは 1.15 GB・0.40 秒）。
- **int8 は GPU では遅い**: 8.5 倍遅く、VRAM もほとんど減らない。int8 の計算（動的量子化）が MIGraphX で速くならない。
  int8 は CPU 向けの選択（CPU では fp32 より速い）。
- fp32 の ONNX を後から fp16 へ直す方式（onnxconverter-common）は、Cast の型が合わず読み込めなかった。重みを fp16 で読んで
  そのまま書き出すと、元の点数との差は最大 0.0002。
- MIGraphX は形ごとにコンパイルする（初回 30 秒前後、RAM を一時 6 GB ほど使う）。結果を保存すると次からは 2〜4 秒で起動する（0.64 GB）。
- 容量（GPU の ruri を入れたとき）: モデル 0.63 GB＋コンパイル結果 0.64 GB＋実行環境 約 0.2 GB。変換が済んだら元の重み（1.26 GB）は消す。

## 次の判断（利用者）

1. ruri-v3-reranker-310m を CPU の reranker として足し、日本語の RAG の並べ替えに使う（Knowledge・大きい会話の資料）。
   点数で切る門には使わず、上位の件数で入れる。
2. 会話の流れを指す質問の取りこぼしを防ぐため、大きい会話の資料では、並べ替えの質問に直前の話題を添える。
3. 英語の比重が大きいなら、Qwen3-Reranker-0.6B（CPU、英語 0.60・会話の流れも拾う）を英語の質問に使う選択肢を残す。
