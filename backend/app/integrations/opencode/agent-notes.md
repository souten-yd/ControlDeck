# 文脈の使い方

文脈には上限があり、超えると会話が続かなくなる。実測（262,142 トークンで打ち止め
になった会話）の内訳は、道具の結果が 48.1%、推論が 20.3%、人が読む本文は 1.9%
だった。道具の結果の内訳は bash が 178k 文字、read が 135k、edit が 95k で、
read のほとんどは「探しものが在るかどうかを見るために全文を読んだ」ぶんだった。

## ファイルは当たりを付けてから読む

- まず `grep -n` で行番号を出し、その周りだけを読む。
- 全文を読むのは、短いと分かっているときだけにする。
- 何が在るかを知りたいだけなら、`ls` や `rg --files` や `head` で足りる。

## コマンドの出力は絞ってから受け取る

- 試験は静かに走らせ、落ちたところだけを見る（例: `pytest -q 2>&1 | tail -30`）。
- ログは `grep` で絞る。`cat` で全部を流さない。
- 長くなると分かっているものは file へ落とし、そこから必要な行だけを読む。

## Add-on の道具

- 一覧の説明に「契約はこの一覧に載せていない」と書かれている道具は、
  `control_deck.tool_contract` に `{"name": "<道具の名前>"}` を渡して契約を
  読んでから呼ぶ。透過や感情のような前提は契約にしか書かれていない。
- 結果が長いものは削って返る。全文の置き場は結果の末尾に書いてある。
  必要なところだけを `grep` や `jq` で読み、全文を読み直さない。
- 2 件以上を作るときは batch を使う。1 件ずつ呼ぶと、その都度ホストが
  言語モデルを降ろして載せ直し、会話の文脈を読み直す。
